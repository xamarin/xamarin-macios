# Build targets for iOS, Mac Catalyst, macOS and tvOS

The following build targets are defined in .NET for iOS, Mac Catalyst, macOS, and tvOS projects.

## Build (Default)

Builds the source code within a project and all dependencies.

## Clean

Removes all files generated by the build process.

## ComputeAvailableDevices

Queries and returns a list of available iOS or tvOS devices and simulators that can be used with `dotnet run`.

This target is called automatically by the .NET SDK's `dotnet run` command to
support device selection via the `--device` option. It returns a `@(Devices)`
item group where each device has the following metadata:

- **Description**: The name of the device (e.g., "iPhone 16 - iOS 26.0" for simulators, "My iPhone 16" for physical devices)
- **Type**: Either "Device" or "Simulator"
- **OSVersion**: The OS version of the device
- **UDID**: The UDID of the device
- **RuntimeIdentifier**: The RuntimeIdentifier of the device

For example, to list all available devices:

```shell
$ dotnet build -t:ComputeAvailableDevices
```

This target is part of the [.NET SDK device selection specification](https://github.com/dotnet/sdk/blob/2b9fc02a265c735f2132e4e3626e94962e48bdf5/documentation/specs/dotnet-run-for-maui.md) and enables commands like:

```shell
$ dotnet run --device UDID
```

Added in .NET 11.

## DeployToDevice

Deploys an already-built iOS or tvOS app to a device or simulator without
building it again. A specific deployment target can be selected with the
`$(Device)` property.

```dotnetcli
dotnet build -t:DeployToDevice project.csproj -p:Device=<udid>
```

The .NET SDK calls this target during `dotnet run`, including when the
`--no-build` option is specified.

Added in .NET 11.

## GetApplicationArtifacts

Builds the project and returns the `@(ApplicationArtifact)` item group. This
target always runs `Build` first so platform `.app`, `.ipa`, `.pkg`, and
`.xcarchive` artifacts are produced and collected before any custom metadata
extension targets run. The `Publish` target returns the same item group for
artifacts it creates.

The returned item group reflects the artifacts the current invocation is
configured to build; it does not scan for `.ipa`, `.pkg`, or `.xcarchive` files
left on disk by a previous build. The `.app` bundle is always collected for an
application project (excluding app extension and watch app projects), while the
`.ipa`, `.pkg`, and `.xcarchive` outputs are only collected when
[BuildIpa](build-properties.md#buildipa),
[CreatePackage](build-properties.md#createpackage), or
[ArchiveOnBuild](build-properties.md#archiveonbuild) (respectively) is enabled in
the same invocation. The `Publish` target enables `BuildIpa` (mobile) or
`CreatePackage` (desktop) by default.

```shell
$ dotnet build MyApp.csproj -t:GetApplicationArtifacts -getItem:ApplicationArtifact
$ dotnet build MyApp.csproj -t:Publish -getItem:ApplicationArtifact
```

See [ApplicationArtifact](build-items.md#applicationartifact) for supported metadata.

Targets that need to add or update `@(ApplicationArtifact)` metadata before
`GetApplicationArtifacts` or `Publish` returns can append to
[GetApplicationArtifactsDependsOn](build-properties.md#getapplicationartifactsdependson).

## Run

Builds the source code within a project and all dependencies, and then deploys and runs it
on a default simulator/device. A specific deployment target can be set by using the `$(Device)` property.

```dotnetcli
dotnet build -t:Run project.csproj -p:Device=<udid>
```

## RunIPadAppOnMac

Builds an iOS application and runs it directly on an Apple silicon Mac, without
using a simulator or rebuilding for Mac Catalyst. The app must support iPad
(`UIDeviceFamily` must contain `2`) and target the `ios-arm64` runtime identifier.
Both iPad-only and universal iPhone/iPad apps are supported.

Eligible projects also list **My Mac (Designed for iPad)** among the destinations
shown by `dotnet run --list-devices`. Select it using `--device`:

```dotnetcli
dotnet run --project project.csproj --device "My Mac (Designed for iPad)"
```

This builds the project for `ios-arm64` before launching it. Use `--no-build` to
launch an existing device build without rebuilding. An explicitly selected
simulator runtime identifier excludes the Mac destination.

The equivalent build-first MSBuild target is:

```dotnetcli
dotnet build project.csproj -t:RunIPadAppOnMac -p:RuntimeIdentifier=ios-arm64
```

For a multi-targeted project, also specify the iOS target framework with `-f`.
The ordinary `Run` target also accepts `-p:Device="My Mac (Designed for iPad)"`
when the project has already been built for `ios-arm64`.
Use a valid development signing identity and provisioning profile that includes
the Mac's provisioning UDID. You can find this identifier using
`system_profiler SPHardwareDataType`.

The target creates a fresh wrapper around a copy of the signed app in the
intermediate output directory, then launches the wrapper with macOS Launch
Services. The original app bundle is not modified. A new wrapper is required
for each invocation because macOS protects previously launched iOS app bundles
against in-place updates. `Clean` removes these wrappers.

By default, the target waits for the app to exit. Set `WaitForExit=false` to return
after launching. Standard output and standard error are forwarded to the current
terminal, when one is available. Set `StandardOutputPath` and `StandardErrorPath`
to capture the app's output in specific files, or `StandardInputPath` to redirect
its input. Application arguments after `dotnet run --` and
`RuntimeEnvironmentVariable` items are forwarded to the app.
This target does not attach a managed debugger.

`dotnet test` is not currently supported for this destination: Microsoft Testing
Platform's named-pipe connection requires Unix-domain sockets, which the pinned
iOS runtime reports as unsupported. The runtime change in
[dotnet/runtime#135167](https://github.com/dotnet/runtime/pull/135167) removes this
restriction, but is not yet included in the runtime dependency used here.
Launching a test app with `dotnet run` does not establish the `dotnet test`
protocol. Also, macOS `open` does not propagate the app's exit code, so its success
must not be interpreted as a passing test run.

The wrapper layout used for local launching is not a documented Apple deployment
interface. This target does not support Intel Macs, iOS simulator builds,
iPhone-only apps, or other platforms than iOS.
